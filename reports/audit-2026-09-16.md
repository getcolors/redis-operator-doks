## Headline verdict

The safety core holds: an ambiguous observation never becomes a create or a
destroy, `compute-prevent-destroy` stays on during converge and is lifted only
by an explicit `Destroy` deletion, the self-heal script proves ownership three
ways before its one DELETE, and no secret was found on any log, status,
evidence, argv or stdout path. The self-healing headline (5m46s recovery,
generations 3→4→5, worker untouched) is supported by the evidence files.

Everything around that core is thinner than the handoffs say. The most
important gaps, across repos, in order:

1. **Unexplained third Droplet.** `redis-doks/evidence/live-resources.json`
   (16:19 UTC) records Redis Droplet 600724611 as the active host after all
   tests. `evidence/shutdown.json` (17:11 UTC) records deleting 600730033.
   No file, commit or prose explains a second replacement in the 52 minutes
   between. Combined with two unexplained first-attempt Ansible failures (both
   creates, no logs retained), the "recovery verified" claim covers less than
   the HANDOFF states.
2. **A DigitalOcean 404 is token-relative** (`redis-operator/src/colors/redis.clj:80,112-119`).
   A Droplet in another team returns 404. Rotate the Secret to a token from a
   different team and the operator "confirms absence", tofu refresh agrees,
   and a second Droplet is created in the new team while the original keeps
   running orphaned. No account identity is recorded or checked.
3. **Termination grace is shorter than the worst-case workflow**
   (`redis-operator/src/colors/install.clj:31` = 7500 s; the Ansible play alone
   is capped at 7200 s in `redis/green/.../tools.clj:187`, plus tofu plan up to
   1800 s). A SIGKILL mid-infrastructure leaves the compute journal lock held,
   and the pinned colors-compute ae28ea7 has no repair path; that repair
   arrived in 7e1c234, one commit later. Result: permanent `ExecutionFailed`
   needing manual journal surgery.
4. **The green controller's 409 branch never fires with the real client**
   (`green/src/green/kubernetes.clj:189` vs `kubernetes/client.clj:74-75`,
   which throws `{:exit n}` and discards the HTTP status). Tests pass because
   the fake throws `{:status 409}`. Consequence: a transient failure on the
   final Ready publish is followed by a `failure!` write, so a successful
   converge can be reported as `Failed/ExecutionFailed` with backoff.
5. **No logging anywhere, in either controller.** Green counts errors in an
   atom nobody reads, catches only `Exception` so an `Error` kills a worker or
   the poller silently, and ships no liveness or readiness probe. The Redis
   adapter drops `:green/err` and raw workflow output entirely. In-cluster
   diagnosis means exec into the pod and rerun by hand.
6. **DOKS discards all OpenTofu output** (`doks/src/colors/doks.clj:55-62`).
   A held state lock (whose Lock ID you need for force-unlock), a
   `prevent_destroy` refusal, a retired version slug, a backend change, or an
   R2 403 are all "OpenTofu plan failed (exit 1)". The stated rationale
   (provider diagnostic leakage) is weak; `green.tofu/fail` already puts
   stderr into `:green/err` as the SDK convention.
7. **Benign provider drift causes a permanent restart loop**
   (`redis.clj:98-104`): `provider-matches?` requires `image.slug` and
   `size_slug` equality. DO nulls the image slug when a base image retires;
   an external resize changes the size. Either makes `matches?` false forever,
   so every reconcile interval (30 s in redis-doks) reruns the full create
   workflow, whose smoke gate restarts Redis.
8. **Two Destroy paths are untested or wedge.** The missing-Droplet delete
   (`redis.clj:148-154`) is a private two-step workflow that skips every
   package validator; no test reaches it. Destroy on a `"partial"` deployment
   hits `compute inspection refused` forever, and the only exit (Retain)
   orphans the declared resources.
9. **Suspension is a one-shot check, not a lease** (`probe.clj:28-33`,
   `redis-doks/scripts/rehearse.py`). Sound within one controller process at
   the instant checked, but a delete or unsuspend after the check runs the
   controller concurrently with a two-hour rehearsal. `rehearse.py`'s
   `finally` makes another kubectl call that can mask the original error and
   leave the CR silently suspended; Ctrl-C shows only a traceback.
10. **The restart test proves less than claimed.** No readiness probe plus
    per-start dependency resolution (`~/.gitlibs` is not on the PVC) means the
    new pod is "ready" before the controller has loaded; `wait_active_ready`
    returns on the stale Ready status. The whole test took 64.8 s including a
    45 s sleep and never reads `status.lastReconcileTime`.
